Engineering assessment · Image & video generation

Why one Altitude renders better creative than the other

Both codebases generate the same deliverables. Only one of them talks to the image model properly. This is what separates them, and what it takes to close the gap.

Repo A AltitudeX-MAIN-SANDBOX · 92k LOC backend Repo B altitude (Altitude-backend-main + Frontend) · 60k LOC backend Read source only — no runtime access

The short answer

Repo B never actually asks for a good image

Repo A owns its image pipeline end to end: it runs a reasoning model to author a scene, layers roughly thirty brand/product/audience directives on top, attaches reference photos grouped by role with per-group instructions, and renders on Nano Banana Pro at 2K–4K.

Repo B is a thin orchestration layer in front of an external content-agents service. It takes whatever spec that service returns, flattens ~20 fields into a "key: value. key: value." string — resolution labels and internal variant names included — attaches an undifferentiated list of product photo URLs, and renders on Imagen 4 at default resolution.

The quality difference is not a model licence or a budget. It is that repo A's prompt is a brief and repo B's prompt is a database row.

Root causes, ranked by effect on output

Eight concrete differences

Each of these is verifiable in source. The first four account for most of what the client is seeing.

01

Different image model, and the weaker one cannot render type

Dominant cause

Imagen 4 is a strong scene generator but is poor at legible in-image typography and does not accept reference images at all — repo B's own code notes that content-agents only swaps to gemini-2.5-flash-image when reference images are present. Nano Banana Pro (gemini-3-pro-image) renders headlines, logos and wordmarks as real advertising typography, which is exactly the "looks like a finished ad" quality the client is responding to.

Repo A

Default gemini-3-pro-image, called through generateContent() so references ride along as inline parts. Four selectable Nano Banana tiers exposed in Playground.

backend/src/common/gemini/models.ts:41 · gemini.client.ts:675

Repo B

Tier aliases map only to Imagen 4 (standard/fast/ultra). Config default VERTEX_AI_IMAGE_MODEL=imagen-4.0-generate-001. No caller in the platform path ever sets model, so every render is Imagen 4 unless references happen to be attached.

…/asset-generation/services/vertex-ai.service.ts:6 · src/config/app.config.ts:77
02

The prompt is a serialized record, not a brief

Dominant cause

buildImagePrompt() joins about twenty spec fields with ". ". Several of those fields are internal metadata that the image model reads as scene content: Dimensions: 1080x1080, Required dimensions:, Image name:, Variant: B, Meta prompt used:. Diffusion models do not ignore stray tokens — they render them as texture, labels, and layout noise.

// repo B, what actually reaches the model
"A bowl of ramen. Negative prompt: blurry. Style: modern.
 Mood: warm. Dimensions: 1080x1080. Image name: ig_square_v2.
 Color palette: #fcb514, #1a1a1a. Variant: Variant B. ..."

Repo A

A reasoning model first authors a structured execution JSON — scenePrompt, negativePrompt, brandApplication, composition.safeZones, referencePlan — against a content-type-specific system prompt with an art-director persona and craft standards. The handler then layers conditional directive blocks for headline typography, logo lockup, palette, motifs, treatment, audience ethnicity, product fidelity and size-aware layout.

backend/src/common/prompts/execution-prompt/ · worker/handlers/generate-visual.handler.ts:420–1440

Repo B

No authoring step on your side. Whatever content-agents returns is flattened and shipped, metadata included.

…/services/asset-generation-helper.service.ts:322–398
03

Reference images are untyped, so the model treats them all as vague style hints

Dominant cause

This is repo A's single cleverest piece of engineering. References are grouped into five roles, and each group is preceded by its own instruction text before its images — a "sandwich" that tells the model which pictures are ground truth and which are mood.

Repo A · five roles, five instructions

master follow ~85–90% · product reproduce 100% identically · reference follow ~60–70% for style only · logo reproduce exactly, case-sensitive · avatar reproduce the face faithfully.

Images are sent as inline base64 after a normalization pass that transcodes SVG/AVIF/GIF to PNG and drops undecodable files — an unsupported format otherwise makes Gemini reject the whole request.

gemini.client.ts:92–102, 700–745 · common/gemini/reference-image-normalize.ts

Repo B · one flat list

reference_images: string[] — URLs, all from the product-photo tier, capped at 10. No role, no per-group instruction, no logo reference, no style reference, no campaign hero. No format normalization.

…/services/product-reference-images.service.ts
04

Repo B has excellent brand data and never sends it to the image model

Dominant cause

This is the most fixable finding in the report. altitude-brand-management-service/src/modules/brand-management/brand-dna.ts defines a genuinely good canonical Brand DNA: colours as {name, hex, role}, typography, visual.renderMode, visual.treatment, graphicMotifs, logo variants and don'ts, compliance must-include/must-avoid.

In the render path, none of it is used. renderImage() passes only brand_pack_id, and the code's own comment says: "Additive — content-agents ignores it until the render-time brand-lock ships." getBrandPack() exists but its only occurrence in the content service is its own definition. The brand pack is consumed solely by the Fabric overlay builder, for text fonts and colours drawn on top of the image.

Repo A injects it directly

Palette by name + exact hex ("treat the HEX as ground truth"), background-colour restriction to main colours only, motif vocabulary, visual treatment repeated identically across Social/Print/Kiosk so one campaign reads as one campaign, and an explicit rule against inventing split colour-field backgrounds — a named, observed failure mode.

generate-visual.handler.ts:762–810 · execution-prompt/constants/brand-style-rules.ts

Repo B leaves it on the table

The image model sees Color palette: #fcb514, #1a1a1a buried in a concatenated string, and nothing else.

…/asset-generation/services/vertex-ai.service.ts · content/services/fabric-template.builder.ts
05

No resolution control — print formats render at ~1K

Strong contributor

Repo A's size registry carries a per-format minGenImageSize of 2K or 4K, raised further when the user picks HD, and passes it as imageConfig.imageSize. A standee or A4 page asks for 4K natively. Repo B sends only width/height/aspect_ratio; there is no resolution parameter anywhere in the render path, so a print asset gets the model default and is then upscaled or simply looks soft.

Repo A

resolveImageSize() takes the higher of the registry floor and the quality choice.

common/content/content-sizes.ts · generate-visual.handler.ts:162

Repo B

toRenderableImageShape() correctly drops un-renderable print dimensions, but nothing replaces them with a resolution request.

…/services/asset-generation-platform.service.ts
06

Clean plate plus vector text reads as a template; baked type reads as an ad

Strong contributor

Repo B's render_mode: 'editable' produces a deliberately text-free background and draws copy as Fabric.js objects. That is the right call for editability — and it is a real product advantage — but flat vector type sitting on a photo is precisely the "made in a tool" look. Repo A takes the opposite default: Nano Banana Pro bakes the headline as real advertising typography, matched to the weight and personality of the brand's own typeface, with the deterministic pixel compositor reserved for IAB display banners where exact pixel placement matters more than craft.

Note that repo B already hit and fixed the halfway-house bug here — overlay copy was being fed into the render prompt and drawn on top, producing doubled text (asset-generation-helper.service.ts:365).

07

No campaign-level visual anchor

Strong contributor

Repo A generates a master creative once per campaign loop, then feeds it into every subsequent format as the master-role reference with instructions to stay 85–90% consistent with its art direction while re-composing for the new aspect ratio. Repo B renders each platform spec independently. Its team already noticed and partly addressed the symptom — docs/asset-generation-render-fixes.md Part 2 consolidated per-spec Content Agents calls because "a platform's video showed a completely different creative concept than its image" — but consolidating the text call does not give the image model a shared visual anchor.

08

Blocked renders fail silently; video defaults to the cheapest tier

Reliability, and one easy win

Gemini frequently blocks prompts containing "reproduce this branded product identically" wording with blockReason: OTHER. Repo A detects an empty-but-blocked response and retries once with softened IP language via softenImagePromptText(), behind a per-model circuit breaker and transient-retry wrapper. Repo B has no equivalent — a failed spec becomes gcsUri: null and the asset is quietly absent. That alone can look like "sometimes the images just aren't good".

On video: both renderVideo() and renderVideoBatch() default to render_tier: 'lite' — by the file's own comment the $0.40 tier, against $2.00 fast and $3.50 full. Nothing in the platform path overrides it. Repo A deliberately bumped its default from Veo 3.1 Fast to the full quality tier, with the reasoning recorded in the model map.

Repo A

Circuit breaker + transient retry + soft retry on block. Veo 3.1 quality tier, storyboard frames as first/last-frame anchors, segment plans, audio prompts, montage close.

gemini.client.ts:836–860 · worker/handlers/generate-videos.handler.ts

Repo B

No retry on block. render_tier ?? 'lite' in both video paths. No first/last frame, no negative prompt sent for video, refs capped at 3.

One decision gates everything

Do you control content-agents?

The content-agents service is not in either repository on this machine. It is reached only over HTTP at CONTENT_AGENTS_URL, with a tenant slug header. Its internals are referenced in comments as Python (schemas/content.py, render.py, versions "v52+", "v55+"). Everything about model choice, reference conditioning and render-time brand lock happens in there.

What I need from you

Five questions, in priority order

Phases 1 and 2 can start before any of these are answered. Phase 3 onward cannot.

1 · Who owns content-agents?

Your team, another team in the client's org, or a vendor? Can you get me the repo, or at least its OpenAPI spec?

This is the fork in the plan. It changes where roughly 60% of the work lands and swings the estimate between 2 and 6 weeks.

2 · Is repo A the target, or a reference?

Are we improving repo B to ship, with repo A as the quality benchmark? Or is the long-term plan to merge them?

If they merge, I would sequence this very differently — port B's versioning and editor into A rather than porting A's renderer into B.

3 · What is the cost ceiling per asset?

Nano Banana Pro at 4K costs materially more than Imagen 4 at 1K, and Veo full is roughly 9× lite. Repo A's model map states its position plainly: "Quality trumps cost for content generation."

If there is a hard per-asset budget, I would keep Nano Banana Pro for hero and print formats and use a cheaper tier for high-volume social — a split repo A already supports through its four selectable tiers.

4 · Do you have paired examples?

Ten or so cases where the same brand and brief produced a good image in A and a poor one in B — ideally with both prompts.

The eight causes above are derived from source. Paired examples would let me rank them by your actual failures rather than by my reading, and would seed the Phase 5 evaluation set.

5 · Does the editable canvas have to stay the default?

Fabric overlays and baked typography pull in opposite directions. Repo A's output looks finished partly because the type is in the pixels.

If editability is non-negotiable for every asset, Phase 4's typography step becomes opt-in and the ceiling on "looks like a real ad" is a bit lower. Worth deciding deliberately rather than by default.
